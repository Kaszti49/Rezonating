## @bench
**2026-10-13, the deep-engineer measurement behind D-022.** A 10-minute recording had lost samples. The sidecar only said how many. The pipeline had to assume every all-zero frame might be a lost one. On a quiet floor that threw away about 80 % of the footstep windows, though most of those frames were real.

Storing *where* the losses are fixed it. This lesson follows the data from the ADC to a decision, and shows why each file and each rule exists.

## @intuition
### A recording is a photo album with a caption page

Think of one recording as a photo album.

- The **WAV** is the photos: just the numbers, in order, nothing else.
- The **[[sidecar]]** is the caption page. It says when and where the photos were taken, with what camera (the sensor head), the real shutter speed (the *measured* sample rate), and which photos are missing (the losses).
- A **[[pack]]** is a person who looks through the album for one thing: footsteps, falls, or a washing machine. Year 1: `footstep-id` first, then `fall`, then `appliance`.

### Holes, not guesses

A lost sample is stored as zeros in the WAV. Zeros look like data, so the sidecar must say where they are. First it only said *how many*. Now it also lists the **[[loss-span|loss spans]]**: pairs `[start, length]`.

### Why keep the raw 2 kSPS

{{predict:1}}

> [!warn] Where the analogy breaks: a photo album's captions are written by a person who can look at the photos. The sidecar is written by a machine at recording time, so it can only state what the machine counted. That is why "count every sample" matters.

### From samples to a decision

footstep-id works like a security guard. It waits until the floor is much louder than usual (the trigger), cuts out half a second around that moment, measures the shape of the step (features), and asks a small model whose step this was.

### The sidecar, field by field

| Field | Holds | Our example |
| --- | --- | --- |
| `sample_rate_nominal` | the rate we asked for | 2000 |
| `sample_rate_measured` | the rate DRDY really ran at | 1995.80 (bench, 2026-11-01) |
| `sample_rate` | WAV header, rounded measured rate | 1996 |
| `stream` | which node stream | `adc_raw` |
| `loss` | `device`, `link`, `host` counts | 0 / 0 / 0 on a clean run |
| `loss_spans` | `[i, n]` pairs, sorted, no overlap | `[1200, 4]` and `[5000, 7]` |
| `channels[]` | head, serial, units, gain, scale | `geophone/sm24`, gain 1–128 (PGA) |
| `labels[]` | time ranges and `person` | `"person": "P2"` |

The pseudonym rule: labels hold `P1`, `P2`, …, never a name. The list behind them is not in the repo.

### The pack pipeline (D-021)

`packs/footstep-id/pack.json` names the stages in order:

1. **decimate**: 63-tap FIR, 2 kSPS → 1 kSPS (the same filter as the firmware).
2. **dsp**: high-pass 5 Hz and low-pass 400 Hz, each one 2nd-order Butterworth biquad.
3. **trigger**: [[sta-lta|STA/LTA]], `sta_ms` 50, `lta_ms` 2000, `ratio` 3.5, `pre_ms` 100, `post_ms` 400.
4. **features**: `footstep_v1`, 13 values per window (energy, peak, duration, band energies; a first, simple set that may change).
5. **model**: a classifier; labels `P1`, `P2`, `P3`, `unknown`.

{{calc:2}}

Every stage knows about lost samples. A window with any invalid sample is not guessed at: it is skipped and counted (`n_windows_skipped_invalid`).

### What footstep-id outputs

From `pack.json`: two outputs. `step` (an event: a footstep happened) and `person` (a sensor value, "Last person"). Over the link they travel as EVENT frames: kind 0 is a bare trigger carrying the STA/LTA ratio, kind 1 a pack output with a label. The target for the pack is 85 % person-ID accuracy; no result has been measured yet.

### The model on the device

The plan (D-006): train in Python (scikit-learn for the baseline, always reported next to a majority-class baseline, split by session, never by random clip), then export an int8 TFLite model into `packs/footstep-id/model.tflite`, which [[firmware|firmware]] runs with TFLite Micro. The export is **not written yet**: the pipeline today reports "no model loaded".

### Test vectors

A [[test-vector|test vector]] is a fixed input with the output both languages must reproduce. The model runs with [[tflite-micro|TFLite Micro]] on the node.

```bash
python -m rezonating_ml.vectors --check
```

Vectors exist for the decimator, the biquads, STA/LTA and `footstep_v1` (`ml/tests/vectors/`). Each has lost-sample cases. The decimator is already ported to C and tested against its vectors. The firmware's STA/LTA and features are not written yet, so "one feature implementation, two languages" is not met until they are.

### What the rules mean for us

- **The mask must mark every lost sample.** A lost sample left valid runs through the high-pass as a step and can trigger a false event. A good sample marked lost only costs data. So when unsure, mark lost.
- Spans must be sorted, inside the WAV, zero-filled, and total the `loss` sum. `python tools/validate.py` checks sidecars.
- Never commit raw `*.wav` files or the name list behind P1, P2.
- `fall` and `appliance` use the same shape of pipeline later; their details are not part of this lesson.
